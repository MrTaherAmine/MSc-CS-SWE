# Short Reflection Report

The most difficult part of the schema refactor was balancing the new analytical and availability requirements without damaging the original transaction-oriented design. The first schema was optimized for product browsing and order processing, so embedding order items and customer snapshots reduced the need for joins and made common queries predictable. However, large analytical queries would eventually compete with operational traffic if every report scanned the main `orders` collection.

The new requirements changed the design in three important ways. First, I introduced sharding so order and product workloads could be distributed horizontally across multiple nodes. Second, I added replication to improve availability and fault tolerance when an individual node or failure domain becomes unavailable. Third, I introduced denormalized analytical collections such as `daily_product_sales` and `daily_category_sales`. These collections accept controlled data duplication in exchange for much faster trend and sales queries.

The refactor also required an explicit consistency decision. Order creation and status transitions still require stronger consistency because they affect customers and business records. In contrast, analytical summaries can be eventually consistent because a short delay does not materially affect a management dashboard. This separation improved scalability by isolating transactional and analytical workloads, improved availability through replicated shards, and improved query performance by replacing repeated full-history aggregation with pre-computed read models. The main trade-off is additional architectural complexity, storage duplication, and the need to monitor synchronization between source data and derived analytics.
